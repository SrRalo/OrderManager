## 3. Row Level Security (RLS)

Todas las tablas tienen RLS habilitado. Ningun usuario anonimo puede acceder a los datos.

### 3.1 Policies de `usuarios`

| Policy | Operacion | Condicion |
|---|---|---|
| `usuarios_select_auth` | SELECT | Todos los autenticados ven todos los usuarios |
| `usuarios_insert_self_or_admin` | INSERT | El usuario puede insertar su propio perfil O un admin puede insertar cualquiera |
| `usuarios_update_admin` | UPDATE | Solo un admin activo puede actualizar usuarios |

### 3.2 Policies de `categorias_menu`

| Policy | Operacion | Condicion |
|---|---|---|
| `categorias_select_auth` | SELECT | Todos los autenticados |
| `categorias_insert_admin` | INSERT | Admin o supervisor activo |
| `categorias_update_admin` | UPDATE | Admin o supervisor activo |

### 3.3 Policies de `items_menu`

| Policy | Operacion | Condicion |
|---|---|---|
| `menu_select_auth` | SELECT | Solo items con `activo = true` |
| `menu_mutate_admin_supervisor` | INSERT/UPDATE/DELETE | Admin o supervisor activo |

### 3.4 Policies de `pedidos`

| Policy | Operacion | Condicion |
|---|---|---|
| `pedidos_select_auth` | SELECT | Admin/supervisor/chef ven todos; meseros ven solo los propios (`mesero_id = auth.uid()`) |
| `pedidos_insert_mesero` | INSERT | `mesero_id = auth.uid()` Y rol mesero/admin/supervisor activo |
| `pedidos_update_chef_admin` | UPDATE | Rol chef/admin/supervisor activo |

### 3.5 Policies de `pedido_items`

| Policy | Operacion | Condicion |
|---|---|---|
| `pedido_items_select_auth` | SELECT | Pertenecen al mesero autenticado O el usuario es admin/supervisor/chef |
| `pedido_items_insert_auth` | INSERT | Pertenecen al mesero autenticado O el usuario es admin/supervisor |

### 3.6 Matriz de Permisos por Rol

| Tabla | admin | supervisor | chef | mesero |
|---|---|---|---|---|
| **usuarios** | SELECT, INSERT, UPDATE | SELECT | SELECT | SELECT (solo perfil propio para INSERT) |
| **categorias_menu** | SELECT, INSERT, UPDATE | SELECT, INSERT, UPDATE | SELECT | SELECT |
| **items_menu** | SELECT, INSERT, UPDATE, DELETE | SELECT, INSERT, UPDATE, DELETE | SELECT | SELECT |
| **pedidos** | SELECT, INSERT, UPDATE | SELECT, INSERT, UPDATE | SELECT, UPDATE | SELECT (solo propios), INSERT |
| **pedido_items** | SELECT, INSERT | SELECT, INSERT | SELECT | SELECT (solo propios), INSERT |
| **transacciones** | *bloqueado* | *bloqueado* | *bloqueado* | *bloqueado* |

## 4. API REST (PostgREST)

El endpoint base es: `https://pxwcjdwozqzahhluvtez.supabase.co/rest/v1/`

Todas las operaciones usan el header `apikey: <SUPABASE_ANON_KEY>` y requieren un JWT valido en `Authorization: Bearer <token>`.

### 4.1 Tabla `usuarios`

| Metodo | Endpoint | Descripcion | Filtros usados en Kotlin |
|---|---|---|---|
| `GET` | `/usuarios` | Listar todos los usuarios | `order=fecha_registro.desc` |
| `GET` | `/usuarios?id=eq.{id}` | Obtener usuario por ID | `select=*`, `limit=1` |
| `GET` | `/usuarios?usuario=eq.{username}` | Buscar por nombre de usuario | `select=*` |
| `GET` | `/usuarios?correo=eq.{email}` | Buscar por correo | `select=*` |
| `POST` | `/usuarios` | Crear usuario | Body: `UsuarioInsert` |
| `PATCH` | `/usuarios?id=eq.{id}` | Actualizar campo | Body: `{ "rol": "..." }` |
| `PATCH` | `/usuarios?id=eq.{id}` | Activar/desactivar | Body: `{ "activo": true/false }` |

### 4.2 Tabla `items_menu`

| Metodo | Endpoint | Descripcion | Filtros usados en Kotlin |
|---|---|---|---|
| `GET` | `/items_menu` | Listar items disponibles | `activo=eq.true&disponible=eq.true&order=id.asc` |
| `GET` | `/items_menu` | Listar todos los activos | `activo=eq.true&order=id.asc` |
| `POST` | `/items_menu` | Crear item | Body: `MenuItemInsert` |
| `PATCH` | `/items_menu?id=eq.{id}` | Actualizar item | Body: campos a modificar |
| `PATCH` | `/items_menu?id=eq.{id}` | Cambiar disponibilidad | Body: `{ "disponible": true/false }` |
| `PATCH` | `/items_menu?id=eq.{id}` | Soft delete | Body: `{ "activo": false }` |

### 4.3 Tabla `pedidos`

| Metodo | Endpoint | Descripcion | Filtros usados en Kotlin |
|---|---|---|---|
| `GET` | `/pedidos` | Pedidos pendientes | `estado=eq.pendiente&order=timestamp_creacion.desc` |
| `GET` | `/pedidos` | Pedidos completados | `estado=eq.completado&order=timestamp_creacion.desc` |
| `GET` | `/pedido_items?pedido_id=eq.{id}` | Items de un pedido | `select=*,items_menu(*)` |
| `PATCH` | `/pedidos?id=eq.{id}` | Cambiar estado | Body: `{ "estado": "en_preparacion" }` |
| `PATCH` | `/pedidos?id=eq.{id}` | Marcar completado | Body: `{ "estado": "completado", "timestamp_completado": "now()" }` |

> **IMPORTANTE:** El endpoint `POST /pedidos` **NO se usa desde el cliente Android**. Los pedidos creados por meseros se gestionan localmente (Room) con identificador `LOCAL-{UUID}` y se emiten via `SharedFlow`. Solo los pedidos remotos (creados via API externa) se almacenan en Supabase.

### 4.4 Tabla `transacciones`

No hay operaciones CRUD desde el cliente. La tabla existe pero esta bloqueada por RLS sin policies.

## 5. Autenticacion (GoTrue)

Endpoint base: `https://pxwcjdwozqzahhluvtez.supabase.co/auth/v1/`

### 5.1 Login

**Archivo:** `SupabaseAuthRepository.kt`

```
POST /auth/v1/otp
```

- Primero busca el usuario en `usuarios` por `correo` o `usuario`
- Luego ejecuta `client.auth.signInWith(Email)` con el correo encontrado
- Retorna el `UsuarioRow` completo

### 5.2 Registro

```
POST /auth/v1/signup
```

1. `client.auth.signUpWith(Email)` con email + password
2. INSERT en `usuarios` con el `id` retornado por GoTrue
3. Retorna el `UsuarioRow` creado

### 5.3 Logout

```
POST /auth/v1/logout
```

- `client.auth.signOut()` limpia la sesion local

### 5.4 Sesion

- `client.auth.currentUserOrNull()` obtiene el usuario actual
- El JWT se almacena automaticamente en el SDK (KeyStore en Android)
- La sesion se renueva automaticamente

## 6. Endpoints del Cliente Android

### 6.1 SupabaseAuthRepository

| Metodo | Descripcion | Supabase Operations |
|---|---|---|
| `login(usernameOrEmail, password)` | Iniciar sesion | Auth `signInWith` + SELECT `usuarios` |
| `register(nombres, correo, usuario, telefono, password)` | Registrar usuario | Auth `signUpWith` + INSERT `usuarios` |
| `findProfileByUsernameOrEmail(value)` | Buscar perfil | SELECT `usuarios` |
| `findProfileBySupabaseId(id)` | Buscar por ID | SELECT `usuarios` |
| `signOut()` | Cerrar sesion | Auth `signOut` |

### 6.2 SupabaseUserRepository

| Metodo | Descripcion | Operacion |
|---|---|---|
| `fetchUsuarios()` | Listar todos | SELECT `usuarios` ORDER BY `fecha_registro` DESC |
| `fetchUsuarioById(id)` | Obtener por ID | SELECT `usuarios` WHERE `id = ?` LIMIT 1 |
| `crearUsuario(...)` | Crear usuario | INSERT `usuarios` |
| `cambiarRol(userId, nuevoRol)` | Cambiar rol | UPDATE `usuarios` SET `rol = ?` |
| `desactivarUsuario(userId, activo)` | Activar/desactivar | UPDATE `usuarios` SET `activo = ?` |

### 6.3 SupabasePedidoRepository

| Metodo | Descripcion | Operacion |
|---|---|---|
| `fetchPedidosPendientes()` | Pedidos pendientes | SELECT `pedidos` WHERE `estado = 'pendiente'` + SELECT `pedido_items` |
| `fetchPedidosCompletados()` | Pedidos completados | SELECT `pedidos` WHERE `estado = 'completado'` |
| `marcarEnPreparacion(pedidoId)` | Cambiar a en preparacion | UPDATE `pedidos` SET `estado = 'en_preparacion'` |
| `marcarCompletado(pedidoId)` | Marcar completado | UPDATE `pedidos` SET `estado = 'completado'`, `timestamp_completado = now()` |
| `createPedido(...)` | Crear pedido | **NO inserta en Supabase** - crea LOCAL con prefijo `LOCAL-` |

### 6.4 SupabaseMenuRepository

| Metodo | Descripcion | Operacion |
|---|---|---|
| `getItemsDisponibles()` | Items disponibles | SELECT `items_menu` WHERE `activo = true` AND `disponible = true` |
| `getAllItems()` | Todos los activos | SELECT `items_menu` WHERE `activo = true` |
| `updateDisponibilidad(itemId, disponible)` | Cambiar disponibilidad | UPDATE `items_menu` SET `disponible = ?` |
| `createItem(...)` | Crear item | INSERT `items_menu` |
| `updateItem(...)` | Actualizar item | UPDATE `items_menu` SET campos |
| `deleteItem(itemId)` | Eliminar (soft) | UPDATE `items_menu` SET `activo = false` |

## 8. Notas y Limitaciones

### 8.1 Pedidos Locales vs Remotos

Los pedidos creados por meseros en la app **NO se almacenan en Supabase**. El metodo `createPedido()` crea un pedido local con prefijo `LOCAL-{UUID}` y lo emite via `SharedFlow`. Solo los pedidos con origen `api_externa` se esperan en la tabla `pedidos` de Supabase.

### 8.2 Transacciones Bloqueadas

La tabla `transacciones` tiene RLS habilitado pero **sin policies**. No es posible realizar ninguna operacion sobre esta tabla hasta que se agreguen las policies correspondientes.

### 8.3 Tablas Planeadas No Implementadas

Segun el plan de implementacion (`docs/plan-implementacion-roles-supabase.md`), estan planeadas pero no creadas:
- `api_keys` - Para autenticar llamadas externas
- `audit_log` - Para registro de auditoria
- Edge Function `crear-pedido-externo` - Para recibir pedidos de sistemas externos

### 8.4 Categorias del Menu

Las categorias se gestionan exclusivamente via seed SQL. No hay operaciones CRUD sobre `categorias_menu` desde el codigo Kotlin.

### 8.5 Sincronizacion Room ↔ Supabase

| Dato | Room (Local) | Supabase (Remoto) |
|---|---|---|
| Usuarios | Cache offline | Source of truth (login/registro) |
| Pedidos | Cola local para offline | Solo lectura de pedidos remotos |
| Items Menu | CRUD completo usado por ViewModels | `SupabaseMenuRepository` existe pero no es usado |

### 8.6 Migraciones SQL

| Archivo | Descripcion |
|---|---|
| `supabase/migrations/20260723220000_initial_order_manager.sql` | Crea todas las tablas y RLS iniciales |
| `supabase/migrations/20260723230000_add_categorias_rls_and_seed.sql` | RLS para categorias + datos semilla |
| `supabase/migrations/20260723230001_add_estado_default.sql` | Defaults para `estado` y `origen` en `pedidos` |
| `supabase/seed.sql` | Datos semilla (categorias + 10 items de menu) |
